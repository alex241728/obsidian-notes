# Singe-Rate Synchronous Dataflow

- Static operators
- Data flows through all operators at same rate
- Efficient in FPGAs
- Can pipeline to increase parallelism
- Want cuts:
	- With equal logic on both sides
	- With few edges (registers)
- Can't pipeline a loop

# Synchronous Dataflow

- What if some operators produce more outputs than input?
	- E.g. Interpolation filter
- Or vice versa?
	- E.g. Decimation filter

- Can't run everything at same rate
- Use **data valid** to tag/synchronize data.

![[synchronous_dataflow.png]]
- Feed forward control: G executes when both inputs valid.
- Choose speeds/copies of $F_{1}$, $F_{2}$, $G$ such that no valid data dropped.

# Dynamic Streaming Dataflow
- What if time to produce data varies?
	- E.g. Newton-Raphson iteration
- What if amount of data varies?
	- E.g. Huffman encoding
- Don't want to (or can't) worst case time/data size

- Convert some pipeline registers to FIFOs.
	- Decouple operators
- Can't bound computation imbalance?
	- Add back-pressure signals
	- Assert in time to avoid b

## Time-Domain Multiplexing

### Scenario

- Some IP Blocks are complex and expensive, as well as faster than 1 stream (For instance, 400 MHz). 
- However, the speed of the data generated by the upstream may be relatively slow, running at, for example, only 200 MHz.
- **Pain Point**: If a costly 400 MHz IP core were dedicated to each input stream, not only one core would always sit idle half of the time, but a significant amount of expensive FPGA area would be wasted.

![[time-domain-multiplexing.png]]

### Key Approach

1. Retain only a single high-cost processing core $H$.
2. Feed data from Stream A and B into a shared FIFO buffer.
3. Add extra bits to the data bus (e.g., just 1 bit here - 0 for Stream A, 1 for Stream B), so the tag travels alongside the data through the pipeline.
4. Upon exiting operator $H$, data is automatically routed to the corresponding output queues ($FIFO^A$ and $FIFO^B$) based on the attached Stream ID.

### Benefits
- Achieves the throughput that originally requires two hardware units using only one
	- Half the core area by leveraging the high-frequency characteristics of the IP core.
- **Distributed Control**: Even if the pipeline stages within the IP core are modified by others, the external interfaces will not malfunction.
