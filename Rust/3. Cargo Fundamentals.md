## 1. Project Directory Structure & Initialization

Cargo enforces a standard layout convention:

```text
my_project/
├── Cargo.toml       # Manifest (metadata & dependency declarations)
├── Cargo.lock       # Deterministic dependency resolution (auto-managed)
├── .gitignore       # Initialized by default (unless inside an existing repo)
├── src/
│   └── main.rs      # Source code root / default binary entry point
└── target/          # Compilation artifacts (debug / release binaries)
```

### Initialization Commands
```bash
# Create a new project directory with standard scaffold
cargo new <project_name>

# Initialize Cargo in an existing directory
cargo init

# Override default VCS setup if needed
cargo new <project_name> --vcs=none
```

---

## 2. Configuration Files: `Cargo.toml` vs `Cargo.lock`

| File | Format / Author | Purpose & Best Practice |
| :--- | :--- | :--- |
| **`Cargo.toml`** | TOML (Manual) | **Package manifest**: Configures package name, version, edition, and high-level crate dependencies under `[dependencies]`. |
| **`Cargo.lock`** | Auto-generated by Cargo | **Reproducibility lock**: Records exact dependency versions and checksums. **Never edit manually.** |

## 3. Core Development Commands & Workflow

```bash
# 1. Fast compile-check (No binary output)
cargo check

# 2. Build development executable
cargo build

# 3. Build & execute in one step
cargo run
```

> [!tip] Why prefer `cargo check` during development?
> Compiling code to machine code binaries takes time. `cargo check` skips the code-generation and linking phases, analyzing only syntax and types. It runs significantly faster, making it the preferred command for rapid iterative checks while editing.

---

## 4. Build Profiles: Debug vs Release

Cargo provides pre-configured optimization profiles:

| Profile | Command | Target Directory | Optimization & Characteristics |
| :--- | :--- | :--- | :--- |
| **Development** (Default) | `cargo build` / `cargo run` | `target/debug/` | Unoptimized, full debug info (`debuginfo`). Faster compile times for iterative development. |
| **Release** | `cargo build --release` | `target/release/` | Heavy compiler optimizations enabled. Longer compilation time, but produces the fastest, smallest binary. |

> [!warning] Benchmarking Caveat
> Always benchmark and evaluate performance using release builds (`cargo build --release`), as debug builds run considerably slower due to missing compiler optimizations.
