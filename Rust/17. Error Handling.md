Rust groups errors into two distinct categories: **unrecoverable errors** (handled via the `panic!` macro, which halts execution) and **recoverable errors** (handled via the `Result<T, E>` enum, which forces the caller to acknowledge and handle potential failures).

---

# 1. Unrecoverable Errors with `panic!`

When an irrecoverable issue occurs or an invariant is broken, Rust invokes the `panic!` macro. A panic can occur through:
1. **Explicit invocation**: Directly calling `panic!("message")`.
2. **Implicit failure**: Runtime operations that fail fundamental safety checks (e.g., accessing an out-of-bounds vector or slice index).

```rust
fn main() {
    panic!("crash and burn");
}
```

## Unwinding vs. Aborting
When a panic occurs, Rust must handle memory cleanup:

| Strategy | Behavior | Trade-offs | Configuration (`Cargo.toml`) |
| :--- | :--- | :--- | :--- |
| **Unwinding** *(default)* | Walks back up the stack, running destructors (`drop`) and cleaning up data for each frame. | Safer resource cleanup, but produces slightly larger binaries. | Default behavior. |
| **Aborting** | Terminates the program immediately without cleaning up stack memory (delegating cleanup to the OS). | Yields the smallest binary size; faster exit on failure. | `[profile.release]`<br>`panic = 'abort'` |

## Reading Backtraces
When an implicit panic occurs (such as an out-of-bounds index), Rust protects against buffer overread security vulnerabilities by halting execution:

```rust
let v = vec![1, 2, 3];
v[99]; // Panics: index out of bounds: the len is 3 but the index is 99
```

To diagnose the origin of a panic:
1. Run with the environment variable set: `RUST_BACKTRACE=1 cargo run` (or `RUST_BACKTRACE=full`).
2. Debug symbols are required (enabled by default in dev/debug mode).
3. Read the stack trace from top to bottom; locate the first line referencing **source code you authored**.

# 2. Recoverable Errors with `Result<T, E>`

Most errors represent expected operational conditions (e.g., missing files, rate limits). Rust models these via the `Result<T, E>` enum:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

* Both `Result` and its variants (`Ok`, `Err`) reside in the standard prelude and can be used without imports or namespace prefixes.
* `T` represents the success value type, while `E` represents the error type.

## Handling `Result` via `match`
```rust
use std::fs::File;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => panic!("Problem opening the file: {error:?}"),
    };
}
```

## Matching on Specific Error Kinds
The standard library `std::io::Error` provides a `.kind()` method returning an `io::ErrorKind` enum:

```rust
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file = match File::open("hello.txt") {
        Ok(file) => file,
        Err(error) => match error.kind() {
            ErrorKind::NotFound => match File::create("hello.txt") {
                Ok(fc) => fc,
                Err(e) => panic!("Problem creating the file: {e:?}"),
            },
            _ => panic!("Problem opening the file: {error:?}"),
        },
    };
}
```

> [!tip] Functional Alternative: Combinators
> Deeply nested `match` statements can be simplified using closure-based combinators such as `.unwrap_or_else()`:
> ```rust
> let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
>     if error.kind() == ErrorKind::NotFound {
>         File::create("hello.txt").unwrap_or_else(|error| {
>             panic!("Problem creating the file: {error:?}");
>         })
>     } else {
>         panic!("Problem opening the file: {error:?}");
>     }
> });
> ```

# 3. Ergonomic Panics: `unwrap` and `expect`

When you want to assert success or intentionally crash on failure without writing full `match` blocks:

## `unwrap()`
Returns the inner `T` if `Ok`, or calls `panic!` with a generic default message if `Err`:
```rust
let greeting_file = File::open("hello.txt").unwrap();
```

## `expect("custom message")`
Behaves identically to `unwrap`, but includes a developer-supplied error message in the panic output:
```rust
let greeting_file = File::open("hello.txt")
    .expect("hello.txt should be included in this project");
```

> [!important] Production Best Practice
> Prefer `expect` over `unwrap`. Supplying context clarifies the assumption behind the operation and dramatically simplifies root-cause analysis during post-mortem debugging.

# 4. Error Propagation & The `?` Operator

Rather than handling an error locally, idiomatic Rust functions often **propagate** errors back to the caller using the question mark operator (`?`):

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username_file = File::open("hello.txt")?;
    let mut username = String::new();
    username_file.read_to_string(&mut username)?;
    Ok(username)
}
```

## How the `?` Operator Works
* If the value is `Ok(T)`, it unwrap-evaluates to `T` and execution continues.
* If the value is `Err(E)`, it triggers an immediate early `return Err(...)` from the enclosing function.
* **Automatic Error Conversion (`From` Trait)**: Error values processed by `?` pass through `From::from`. If the function returns a custom error type `AppError`, any error that implements `From<io::Error> for AppError` is automatically converted without manual boilerplate.

## Method Chaining with `?`
The `?` operator can be chained inline for concise operational pipelines:

```rust
fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();
    File::open("hello.txt")?.read_to_string(&mut username)?;
    Ok(username)
}
```

*(Note: In practice, reading an entire file into a string is most succinctly accomplished with the standard library function `fs::read_to_string("hello.txt")`.)*

# 5. Where Can the `?` Operator Be Used?

The `?` operator can only be used in functions whose return type implements `FromResidual`, primarily:
1. Functions returning `Result<T, E>`
2. Functions returning `Option<T>`

## Using `?` with `Option<T>`
When applied to an `Option<T>`, `?` unwraps `Some(T)` or immediately returns `None`:

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}
```

> [!note] Incompatible Types
> You cannot mix `Result` and `Option` seamlessly with `?`. Use `.ok()` to convert a `Result` to an `Option`, or `.ok_or(error)` to convert an `Option` to a `Result`.

## Using `?` in `main()`
By default, `fn main()` returns `()`, which causes compile error `E0277` if `?` is used directly. To use `?` in the entry point, configure `main` to return a `Result`:

```rust
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let greeting_file = File::open("hello.txt")?;
    Ok(())
}
```

* **`Box<dyn Error>`**: A trait object meaning "any kind of error".
* **Process Exit Code**: Returning `Ok(())` exits with status `0`; returning `Err` exits with a non-zero code via `std::process::Termination`.

# 6. Decision Matrix: When to `panic!` vs. Return `Result`

| Scenario | Recommended Approach | Rationale |
| :--- | :--- | :--- |
| **Recoverable / Expected Failure** | `Result<T, E>` | Parsers, network requests, missing files, user input errors. Gives callers control over how to respond. |
| **Examples, Prototypes, Tests** | `unwrap()` / `expect()` | Keeps example code clean; serves as prototyping placeholders; automatically fails test suites. |
| **Developer Has Superior Context** | `expect("justification")` | Compiler cannot prove invariant, but developer knows it's impossible to fail (e.g., hardcoded `"127.0.0.1".parse()`). |
| **Broken Invariants / Contracts** | `panic!` | Caller passed invalid parameters violating documented API preconditions; security or memory safety is compromised. |

# 7. Validation Enforced by the Type System (Newtype Pattern)

Instead of scattering repetitive validation checks throughout function bodies, encapsulate invariants into custom types with validating constructors:

```rust
pub struct Guess {
    value: i32, // Private field prevents unauthorized mutation
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }
        Guess { value }
    }

    // Public getter provides read-only access
    pub fn value(&self) -> i32 {
        self.value
    }
}
```

* **Guaranteed Invariant**: Because `value` is private, any instance of `Guess` is mathematically guaranteed to be within `1..=100`.
* **Zero Repeated Checks**: Downstream functions can accept `guess: Guess` rather than raw `i32` and safely execute without repeating range bounds checks.
